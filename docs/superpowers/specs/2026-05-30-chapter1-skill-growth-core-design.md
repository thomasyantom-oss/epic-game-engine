## 1. 架构决策(本轮拍死,后续 feature 遵守)

### 1.1 技能表示:骨架 + helper + spec(选定方案 a,否决 b 和 DSL)

技能不再是"每个一坨硬编码 JS"。三层分离:

- **skill spec = 数据(YAML)。** 描述技能*是什么*:目标方式、伤害公式参数、命中挂哪个 buff。纯配方,不含逻辑。
- **helper function = 共享执行代码。** 读 spec 把事*做了*:算伤害、扣血、上 buff、拼 log + 动画。跨技能复用。
- **大多数技能零 JS**:声明一个 `effect` archetype(`damage_only` / `buff_only` / `debuff_only` / `damage_with_debuff` / `heal` …)+ 参数,即可。helper 库覆盖 ~80% 技能。
- **结构性技能 fallback 专属 JS**:真正改流程的(弹射、改机制)写专属 handler。引擎有热重载 + JS handler,边际成本几乎为零,且所见即所得。

**示例:**
```yaml
fireball:
  effect: damage_with_debuff      # 命中哪个共享 helper
  damage: { base: 8, scaling: { 智力: 1.2 } }
  debuff: { id: burning, damage: 3, turns: 2 }
  targeting: single_enemy
```

**否决记录:**
- **否决 DSL**(技能效果彻底数据化的描述语言)—— heavy 且无实际意义。
- **否决方案 b**(往技能执行流程的"固定钩子点位"挂 hook 来改写流程)—— b 是为"涌现 / 作者不知道玩家会拼出什么"(Noita 式)准备的,代价是要防 hook 间 conflict、防退化组合、预先拍死钩子点位(= DSL 从后门溜回)。而品类决策(roadmap §4.4/§4.7)**已主动否决涌现**:没有任何技能是玩家自由拼出来的,升级树是作者**亲手画死的有限树**。既然如此,conflict 这个问题根本不该存在(每个节点最终形态作者写死)。用 b = 为一个已被设计掉的问题付架构税。
- **退路(三次法则):** helper 内部关键节点(`after_targeting` / `compute_damage` / `after_hit` …)可**顺手 fire 事件**(EventBus 现成),但**不**把它当正式变换机制设计。等真做了三五个结构性技能、看见反复想插手的点位浮现,b 可平滑长出来,届时点位设计有证据、不拍脑袋。

### 1.2 "技能也有一条 ModifierChain"

技能的**最终 spec = 多来源合并**,不止 node 一个:

```
最终 spec = base spec
          + 自己的升级 node 变换   (Feature 7)
          + 装备改写(roadmap §4.2)(Chapter 2)
          + 别的技能 / 被动打来的 patch(Feature 5)
          + 专精 patch(开关 enabled / 改 scaling / 改主属性)(Feature 6)
```

这是给"技能 spec"做的一条 ModifierChain(属性 ModifierChain 的同构版)。
- **数据层 patch**(改数值、改名、加 tag、开关可用性)走这条统一管道。
- **结构性联动**(狮驼岭鹰击那种"追击 = 插一次额外攻击")仍落专属 JS,不进管道(否则滑回 b)。

这条管道不是单独一段:Feature 1 立骨架(单来源),Feature 4/5/6/7 各自往上加一个 patch 源。

### 1.3 技能 ≠ 跨技能联动(正交,别混)

- **单技能怎么吸收自己的升级** = 方案 a(本文核心)。
- **跨技能联动 / synergy / 连携**(标记→引爆:这回合放标记,下回合火球对被标记目标翻倍)= **独立的一层**,靠 **buff/tag 跨回合传状态**实现(放标记 = 给目标挂 tag,火球 `compute_damage` 时读 tag)。引擎已有 buff/tag。a/b 选哪个都不影响它。

### 1.4 技能实例模型

技能从"全局定义"升级为"玩家拥有、有升级状态"。角色加组件:

```
Skillbook {
  slots: 6,                          # 出战技能位(职业可改;回合制逼出取舍)
  known: [                           # 玩家拥有的技能实例
    { base: "fireball", node: "pyroblast", equipped: true },
    { base: "ice_beam", node: null,        equipped: true }
  ]
}
```
- `base` = 哪个基础技能;`node` = 升到升级树哪个节点(null = 原始);`equipped` = 是否带上场。
- **一个 base 全局只有一个实例**(不能带两个不同升级方向的火球)。
- 执行时:取 `base` spec + `node` 变换 + 其他 patch 源 → 合并 → 喂 helper。

### 1.5 出战 / 被动

- **6 个出战格**,**职业可改**(有的职业天生多/少一格)。6 对回合制打循环够。
- **被动不占出战格**,走自己的轨(被动数量上限待定)。
- **被动两类:** 纯属性被动(+10 攻)→ 走属性 ModifierChain;**特殊效果被动**(鹰击式"有几率追击")→ 一段挂战斗事件的专属 JS。

### 1.6 升级 = 作者手画的有限树

- 升级结果是作者**显式定义的节点**,名字 / 图标挂在节点上(不是单个标签变换硬改名字,否则多变换打架):
  ```yaml
  fireball:
    upgrades:
      - id: pyroblast
        name: "炎爆"
        requires_tag: 爆破          # 消耗的灵魂球
        transforms: [aoe, bonus_hit]  # 引用可复用变换积木
  ```
- **变换(`aoe`/`bonus_hit`)= 底层可复用积木;节点 = 玩家看到的、有名字的东西。**
- **组合不爆炸**:不是 2^N 自由拼,是作者手画的有限树。
- **二次升级 = 节点挂子节点**(炎爆 + 多重 → 某某),深度由作者画,天然有界。**不单独设计。**
- **改 scaling 也是升级的一部分**(炎爆吃 1.5 倍智力)。

### 1.7 可逆性(非对称,刻意)

- **技能升级可花钱重置**(细调旋钮)。对应 roadmap §4.4 红线:"RNG 决定肝多久,不决定角色好不好"——灵魂球不焊死你,坏选择只是损失资源,不是永久变差的角色。重置是 money sink(实现落 Chapter 5),但**Ch1 数据模型要预留 node 可回退**。
- **专精不可洗**(身份级抉择;洗了抉择就没重量)。专精是确定性玩家选择、非 RNG,不可逆不违反 §4.4。

### 1.8 等级:保留,定位明确

- **等级 = 战力的尺子 + 前期地板。** 前期(装备差、技能不全)等级就是强度;后期装备属性加值 ≥ 或 ≫ 升级属性,主导权交给随机产出。
- **每级成长自动固定,不手动分配。** 因为要"等级 = 明确战力";手动分配会让同级两个号强度天差地别,尺子糊掉。build 差异化交给技能树 + 装备承载。
- 已上线的 Experience / 等级系统**留用不推翻**;已做的"手动分配属性点"那套**搁置不删**,留作未来某轨道可能复用。
- **穿装门槛用等级**(干净的标量尺子),**不用**"分配的属性点"(因人而异、难平衡)。

### 1.9 属性表(薄起步,可扩展)

- **基础属性 5 条:力量 / 敏捷 / 智力 / 体质 / 意志。** 地基。
- **二级属性从基础属性派生**(武器攻击伤害、暴击、命中…),先放一两条,后面随便长。
- **伤害类型 + 对应抗性**一层(物理 / 火 / 冰…对抗性),刷子优化空间的大头,要;武器伤害加成归这层。
- **主属性 = 职业 / 专精决定的那条基础属性**(战士→力量,法师→智力)。
- **全套白嫖 2026-05-26 的 ModifierChain**——它支持"衍生自衍生"(按 priority:先算基础属性,二级属性再读已算好的基础属性派生)。职业 / 专精 / 等级 / 装备全往这条链注册 modifier。**引擎不动,纯 mod 数据 + handler。**
- **技能吃属性的方式**:每个技能在 spec 里声明自己的 `scaling`(火球吃 120% 智力)。技能树和装备(Ch2)都挂在**同一张属性表**上 = build 空间的主轴。

### 1.10 专精 = 门 / 灵魂球 = 梯子(正交划分;回答 roadmap §6 deferred"转职/职业树如何与灵魂标签升级共存")

- **专精是整个升级子系统的总闸。** 前期(未专精)= 基础技能组,**不能升级**;**选专精 = 灵魂球升级树整个解锁。** 用一个明确里程碑把 Ch1 最复杂的块 gating 住:前期清爽不劝退,深度在玩家做出"我是谁"的决定后才展开。
- **专精 = 门:** 决定能碰哪些技能 / 哪些升级分支开放;改主属性(战士→盾战士:力量→体质);可能给专属被动。确定性、玩家主动选。
- **灵魂球 = 梯子:** 不管哪个专精,真正往树上爬(火球→炎爆)的**材料**永远是灵魂球,RNG 只在这层。
- **专精开哪些树,灵魂球决定爬不爬得上去。** 不重叠、不循环(避免 §4.6 依赖图成环)。
- 架构上专精就是技能 spec ModifierChain 上的又一个 patch 源,不需要第三套机制。
- **不给专精独立天赋树**(否则又一条成长轨道 = 又一摊平衡)。

## 2. Feature 分解 + 依赖序

Ch1 不是"一个 spec 分三段",是**一组各自独立的 feature**,每个走独立 brainstorm → spec → plan → 实现周期。分细的目的:每段可单独验证、单独讨论数值 / UI、控制每轮 context。

| # | Feature | 含 | 依赖 | 单独深聊点 |
|---|---------|----|------|-----------|
| 1 | **技能架构重构** | 硬编码技能 → `骨架 + helper + spec` 解析;**行为不变(纯重构)** | — | 测试设计、多 case 回归、谨慎不破坏现有实现 |
| 2 | **属性表扩展** | 5 基础属性 + 二级属性派生 + 各职业主属性 + 每条属性的收益 | 1 | 每属性收益 = 数值方案,需具体讨论 |
| 3 | **伤害类型 / 抗性** | 伤害类型层 + 抗性 + 武器伤害加成 | 1, 2 | 数值 / 可玩性设计,需具体讨论 |
| 4 | **Skillbook(出战配置)** | 技能实例模型(base/node/equipped)+ 6 出战格 + 前端配置面板 | 1 | 重要前端 feature,需 UI 设计 |
| 5 | **被动技能** | 被动轨 + 纯属性被动(走 ModifierChain)+ 特殊效果被动(挂战斗事件专属 JS) | 1, 4 | 前后端双改 + case 多,独立讨论 |
| 6 | **专精** | 选专精 + 改主属性 + 开门(gating 升级树)+ 不可洗 | 2, 4, 等级 | 联动职业 / 等级 / 技能,影响最大 |
| 7 | **技能升级树(旗舰)** | 升级树数据格式 + 灵魂球材料 + 节点变换 patch spec + 花钱重置 + debug 给球 | 1–6 | 本体,可能再拆;skilltree(加点)≠ skillbook(列表) |

**排序说明:**
- **#1 是所有人的地基,必须最先。** 纯重构、行为不变,可回归测试保安全。
- **#2/#3 是数值轴**,接着做。
- **#4/#5 与 #2/#3 无强依赖**,先做哪条都行(#4/#5 进入"拥有 / 养成")。
- **#7 是旗舰本体**,依赖前面全部,可能在它自己那轮再拆(树数据 / 灵魂球 / 重置 / UI)。

**关键区分:Skillbook ≠ Skilltree。**
- Skillbook(#4)= "我带哪几个技能"(列表 / loadout)。
- Skilltree(#7)= "火球点成炎爆"(加点 / 升级)。
- 两个不同的前端 + 数据形状,分开。

- **IN:** 升级这台机器的全部机制 + 数据模型 + 前端 + 调试供料。

## 附录 A:关键对话摘录(决策溯源)

> 保留本轮 brainstorm 中决定方向的关键交换,供后续 feature 追溯"为什么这么定"。

**A.1 火球→炎爆的实现哲学(选 a)**
- Claude 提出 a(炎爆 = 独立技能定义,替换槽位)vs b(技能 = 骨架 + 可叠加标签变换)。
- 用户问:b 能改技能名字吗?重构怎么做?
- 结论:改名走"作者显式定义的升级节点"(名字挂节点),组合不爆炸;重构 = 把命令式流程切成有名字的接缝(targeting / damage / on_hit / presentation)。

**A.2 用户背景纠正**
- 用户:"我没开发过上百款游戏,我是**玩过**上百款游戏,本身是个 **backend engineer**。"
- 影响:配置 vs 写死的工程判断 + 玩家对"什么耐刷"的直觉,双重视角。(已据此修正记忆。)

**A.3 spec vs helper 的澄清**
- 用户问:"skill spec 就是 helper function?"
- 结论:不是。spec = 数据(配方),helper = 执行代码(厨子)。常见效果走"共享 helper + YAML 参数",零专属 JS;结构性技能 fallback 专属 JS。

**A.4 a vs b 的真区别(用户一锤定音)**
- 用户起初以为 a/b 是"技能串行 vs 并行处理"。
- Claude 纠正:a/b 与多技能调度无关(都串行);区别在"单个技能怎么吸收自己的升级"。conflict 的尺度是"同一技能多个升级想改同一点位",不是技能 A vs B。跨技能联动是正交的第三层(buff/tag 跨回合)。
- 用户总结:"**b 适用于我都不知道他会怎么升级的情况,a 适用于我已经定义好了升级的树。**" —— 完全正确,且与品类决策(否决涌现)自洽。

**A.5 等级存废(用户拍:保留)**
- 用户:"必须保留等级,等级是非常关键的、比较明确的战力衡量标准。前期等级就是基础属性、是强度的尺子。后期装备属性加值应该略大于或远大于升级属性。"
- 顺带:不喜欢用"分配的属性点"当穿装门槛 → 改用等级当门槛;每级成长自动固定(否则尺子糊)。

**A.6 专精(用户引入 + 拍死规则)**
- 用户:专精到某级可选(战士→盾战士),改主属性(力量→体质),解锁专属技能。
- "**专精解锁之后才能用灵魂球升级,专精解锁之前用基础技能组。**" → 专精 = 升级子系统总闸。
- "**专精不能洗,重要抉择点洗了太麻烦。**" → 可逆性非对称。

**A.7 分解粒度(用户拍:一个 feature 一段)**
- 用户:重构需测试设计;属性扩展含各职业主属性 + 各属性收益,需数值讨论;伤害类型 / 抗性需数值可玩性讨论;Skillbook 是重要前端;被动前后端双改 case 多;专精联动最广;skilltree ≠ skillbook。分细主要为省 token。
